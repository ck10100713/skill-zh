# Team Level

如果沒有帶參數，就輸出使用說明並結束，不要 spawn 任何 agent，也不要讀任何設計文件：
> 用法：`/team-level [level name or area to design] [--review full|lean|solo]` — 指定要設計的關卡或區域（例如 `forest temple`、`tutorial village`、`final boss arena`）。這裡不要用 `AskUserQuestion`，直接輸出說明。

呼叫這個 skill 時：

**決策點：** 每個步驟轉換時，用 `AskUserQuestion` 把 subagent 的提案做成可選項目給使用者選。先在對話中寫出 agent 的完整分析，再用簡短的標籤收下決定。
在 `collaborative` 模式下，使用者核准後才能進下一步。
在 `guided` 模式下，pipeline 會自動往下走，除非某個步驟 BLOCKED；
在 `autonomous` 模式下會從頭跑到尾，每個步驟的結果用 `log_decision` 記錄下來。
屬於 `automation_always_ask` 類別的決策（`is_always_ask_category` helper）不管什麼模式一律要問。參見 `.claude/docs/automation-modes.md`。

## Phase 0: Resolve Config

!`bash "${CLAUDE_SKILL_DIR}/../../hooks/yaml-helper.sh" resolve_config --keys review_mode,automation,team.size`

上面已經解析好了，直接用；`--review` 會覆蓋 `review_mode`。沒有這個區塊的話，就用 `.claude/docs/config-resolution.md` 裡的預設值。

`review_mode` 決定 director gate 的深度，而這條 pipeline 沒有 director gate：
下面任何 phase 在任何 `review_mode` 下，都不會 spawn CD-、TD-、PR- 或 AD-PHASE-GATE。它的 phase gate 就是 pipeline 自己的決策點（定義在下面的 `team.size` 底下），在這些點上工作的 agent 是團隊成員，不是 director gate。

`automation` 決定上面「決策點」那段的行為。各模式如何改變 pipeline 的行為，見上面的決策點說明和 `.claude/docs/automation-modes.md`。

**`team.size`**：哪些 agent 啟用（跟 review_mode 的 gate 深度和 workflow docs 互相獨立）。
- **`individual`**（預設）：只有 `level-designer`。其他 agent 透過 level-designer 諮詢，不會另外 spawn。
- **`small`**：加上 `systems-designer` + `art-director` + `qa-tester`。
- **`studio`**：再加上 `narrative-director` + `world-builder` + `accessibility-specialist`（也就是文件中寫的完整 pipeline）。
在 `individual` 下需要用到的非核心 agent，會改由最接近的核心 agent 處理，並附一則說明。**「Phase gate」指的是這條 pipeline 自己列出、以 `AskUserQuestion` 決策點收尾的任何 phase**：可能是上面「決策點」底下的某個轉換，也可能是下面 pipeline 裡寫明的 **Gate** 步驟，**不管 `automation` 是哪個模式都一樣。** `guided` 和 `autonomous` 改變的是 gate 怎麼通過（自動往下走，或用 `log_decision` 記錄），不是它算不算 gate，所以下面的有界例外條件 (3) 在每個模式下的 gate 都成立。被限制成「只在 phase gate 出場」的 agent，只會在這些時點 spawn，其他時候不會。這個「依啟用名單縮小範圍」的規則適用於下面整條 pipeline：任何 phase 只要點名了啟用名單以外的 agent，就改由最接近的核心 agent 處理，不 spawn 它。

**在 Step 1 之前先公布啟用名單，絕對不准讓縮減悄悄發生。**
spawn 任何東西之前，先用一行講清楚這次實際會 spawn 哪些 agent，以及下面 pipeline 有點名、但在目前 `team.size` 下**不會** spawn 的有哪些。例如：

> `Active set (team.size: <resolved>): <the agents listed for that size above>.`
> `Not spawned this run: <every other agent this pipeline names> — consulted`
> `through <nearest active core agent>. Raise team.size (or modes.rigor) to widen.`

內容要直接從上面的 `team.size` 清單和這個檔案自己的 pipeline 所點名的 agent 填，不要照抄範例。每個 orchestrator 這兩組名單都不一樣。

下面這條 pipeline 看起來像多 agent 的 fan-out，但在預設值下其實只有一兩個 agent：`team-release` 點名了十個、只跑一個，`team-narrative` 在五個 phase 裡點名了六個、只跑 `writer` 一個。**這樣縮減是對的**：`team.size` 是以嚴謹度為前提的，預設收窄就是用來省 token 的。
如果不明講，讀的人就分不出「正確縮減過的 run」和「壞掉的 pipeline」，而上面那條「由最接近的核心 agent 處理並附說明」的規則是在路由當下才觸發，從來不會交代整個 run 的樣子。

這跟這個檔案其他地方的「略過的檢查要回報」是同一條規則：**一個有被執行、卻從沒被講出來的限制，對讀輸出的人來說，跟從來沒執行過的限制看起來一模一樣。**

1. **讀取參數**，取得目標關卡或區域（例如 `tutorial`、
   `forest dungeon`、`hub town`、`final boss arena`）。

2. **蒐集 context**（每份設計文件都要分段讀：用 Grep 工具以 content mode 搜尋 pattern `^#` 找出需要的標題，再用 offset 和 limit 讀那些範圍）：
   - 如果 `design/gdd/game-concept.md` 存在就讀它，或讀 `design/game-brief.md`（在 `rigor: minimal` 時取代它的一頁式 brief），兩者有一個存在就讀
   - 讀 `design/gdd/game-pillars.md` 的遊戲支柱
   - 讀 `design/levels/` 裡現有的關卡文件
   - 讀 `design/narrative/` 裡相關的敘事文件
   - 讀該區域所屬地區／陣營的世界觀文件

## How to Delegate

用 `Agent` 工具把每個團隊成員 spawn 成 subagent：
- `subagent_type: narrative-director` — 敘事目的、角色、情緒弧線
- `subagent_type: world-builder` — 背景設定脈絡、環境敘事、世界規則
- `subagent_type: level-designer` — 空間配置、節奏、遭遇戰、導航
- `subagent_type: systems-designer` — 敵人編組、掉落表、難度平衡
- `subagent_type: art-director` — 視覺主題、色盤、光照、資產需求
- `subagent_type: accessibility-specialist` — 導航清晰度、色盲友善、認知負荷
- `subagent_type: qa-tester` — 測試案例、邊界測試、試玩檢查表

**給每個 agent 的 brief 要精簡，不要整包 context 倒過去。** 共用的輸入只讀**一次**，再把整理過的 brief 直接寫在 prompt 裡：只放每個 agent 真正需要的那幾行，你已經讀過的文件絕對不要只丟檔案路徑（agent 拿到路徑會把整份檔案重讀一遍）。只有你還沒讀、而且只有那個 agent 需要的文件，才給路徑。

**每個 agent 的 prompt 結尾都要加上回傳約定：**「Write your full output to `[path]` — that named path is your write authorisation under the bounded exception below, so write it without a separate approval prompt. Return **only** (1) the path written, (2) a ≤5-bullet summary of decisions, (3) any BLOCKED/CONCERNS items, one line each. Do not restate the documents you read.」沒有這個約定的話，agent 會把它讀過的東西全部倒回這個 session。

**`[path]` 要換成真實路徑。** 工作中的產出放在
`production/levels/[level-name]/` 底下，slug 的規則跟下面「Save to」步驟一樣。每個 agent 一個檔案，這樣平行的步驟就不會共用同一個檔：

| Step / agent | Writes to |
|---|---|
| 1 narrative-director | `production/levels/[level-name]/narrative.md` |
| 1 world-builder | `production/levels/[level-name]/lore.md` |
| 1 art-director | `production/levels/[level-name]/visual-direction.md` |
| 2 level-designer | `production/levels/[level-name]/layout.md` |
| 3 systems-designer | `production/levels/[level-name]/systems.md` |
| 4 art-director | `production/levels/[level-name]/production-concepts.md` |
| 4 accessibility-specialist | `production/levels/[level-name]/accessibility.md` |
| 5 qa-tester | `production/qa/test-cases/[level-name]-cases.md` — test cases, edge cases, playtest checklist, acceptance criteria |

這些是工作草稿；真正留存的紀錄，是你用它們彙整出來的關卡設計文件（`design/levels/[level-name].md`）。

> **為什麼這不違反 Collaboration Protocol。** `CLAUDE.md` 要求 agent 在 Write/Edit 之前先問「May I write this to [filepath]?」。這裡 spawn 出來的 subagent **不問**就寫，這是刻意設計的有界例外，不是疏忽，跟 `consistency-check` 附加寫入 `active.md` 是同一個決定。這個例外只在三個條件**同時**成立時才有效：(1) 路徑是**你**在 prompt 裡指定的，所以使用者核准這個 phase 的時候，就等於核准了目的地；(2) 它是 `production/`、`docs/` 或 `tests/` 底下的新產物，絕對不是改既有的原始碼或設定；(3) 產生它的那個 phase，本身在 pipeline 往下走之前有 `AskUserQuestion` 把關。這三條以外，agent 一定要先問。**不要靠「每個 subagent 都問一次」來「修」這件事**：每個 agent 每個 phase 都跳一次提示，會讓 orchestrator 根本沒辦法用，這就是這個例外存在的原因。

3. **依序統籌關卡設計團隊**：

### Step 1: Narrative + Visual Direction (narrative-director + world-builder + art-director, parallel)

同時 spawn 三個 agent：三個 `Agent` 呼叫都發出去之後，才去等任何結果。

Spawn `narrative-director` agent 來：
- 定義這個區域的敘事目的（這裡會發生哪些劇情節拍？）
- 找出關鍵角色、對白觸發點和背景設定元素
- 指定情緒弧線（玩家進入時、過程中、離開時應該有什麼感受？）

Spawn `world-builder` agent 來：
- 提供該區域的背景設定脈絡（歷史、陣營存在感、生態）
- 定義環境敘事的機會
- 指定任何會影響這個區域遊戲玩法的世界規則

Spawn `art-director` agent 來：
- 為這個區域建立視覺主題目標，這些是配置的 INPUT，不是配置的產出
- 定義這個區域的色溫與光照氛圍（跟相鄰區域有什麼不同？）
- 指定造型語言的方向（稜角分明的要塞？有機的洞穴？衰敗的壯麗？）
- 點名會讓玩家定位方向的主要視覺地標
- 如果 `design/art/art-bible.md` 存在就讀它，所有方向都要以既有的 art bible 為準。要分段讀：先用 Grep 工具（pattern `^#`，content mode）找出需要的標題，再用 offset 和 limit 讀那些範圍。

**art-director 在 Step 1 給出的視覺目標，必須在 Step 2 當成明確的限制條件傳給 level-designer。** 配置決策要在視覺方向的範圍內做，不能先於它。

**Gate**：用 `AskUserQuestion` 呈現 Step 1 的三份產出（敘事 brief、背景設定基礎、視覺方向目標），確認後再進 Step 2。

### Step 2: Layout and Encounter Design (level-designer)
Spawn `level-designer` agent，並把 Step 1 的完整產出當 context 交給它：
- 敘事 brief（來自 narrative-director）
- 背景設定基礎（來自 world-builder）
- **視覺方向目標（來自 art-director）**：配置必須在這些目標的範圍內運作，不能跟它們矛盾

level-designer 要：
- 設計空間配置（主線路徑、選擇性路徑、隱藏要素），確保主要路線跟 Step 1 的視覺地標目標一致
- 定義節奏曲線（緊張高峰、休息區、探索區），跟 narrative-director 的情緒弧線互相協調
- 安排難度漸進的遭遇戰
- 設計環境謎題或導航挑戰
- 定義供尋路用的興趣點與地標，這些必須跟 art-director 指定的視覺地標吻合
- 指定出入口，以及跟相鄰區域的連接

**相鄰區域依賴檢查**：配置產出之後，針對 level-designer 提到的每個相鄰區域，去 `design/levels/` 檢查。如果任何被提到的區域沒有對應的 `.md` 檔，就把這個缺口揭露出來：
> "Level references [area-name] as an adjacent area but `design/levels/[area-name].md` does not exist."

用 `AskUserQuestion` 提供選項：
- (a) 用佔位的參照繼續：在關卡文件裡把這個連接標成 UNRESOLVED，並列在摘要報告的未解跨關卡依賴章節
- (b) 先暫停，執行 `/team-level [area-name]` 把那個區域建立起來

絕對不准替缺漏的相鄰區域編造內容。

**Gate**：用 `AskUserQuestion` 呈現 Step 2 的配置（包含任何未解決的相鄰區域依賴），確認後再進 Step 3。

### Step 3: Systems Integration (systems-designer)
Spawn `systems-designer` agent 來：
- 指定敵人編組與遭遇戰公式
- 定義掉落表與獎勵擺放
- 依預期的玩家等級／裝備來平衡難度
- 設計任何該區域專屬的機制或環境危害
- 指定資源分布（補血道具、存檔點、商店）

**Gate**：用 `AskUserQuestion` 呈現 Step 3 的產出，確認後再進 Step 4。

### Step 4: Production Concepts + Accessibility (art-director + accessibility-specialist, parallel)

**注意**：art-director 的方向性那一輪（視覺主題、色彩目標、氛圍）在 Step 1 已經做過了。這一輪是針對特定地點的製作概念：配置定案後，每個具體空間長什麼樣子？

Spawn `art-director` agent，並把 Step 2 定案的配置交給它：
- 為關鍵空間（入口、關鍵遭遇區、地標、出口）產出特定地點的概念規格
- 指定哪些美術資產是這個區域獨有的，哪些是從全域共用池拿來用的
- 為每個關鍵空間定義視線與光照設置（這些現在是依配置而定，不再是方向性的）
- 指定專屬於這個區域配置的 VFX 需求（天氣體積、粒子、大氣效果）
- 標出任何配置跟 Step 1 目標產生視覺方向衝突的地點，把它們當成製作風險揭露出來

同時平行 spawn `accessibility-specialist` agent 來：
- 檢視關卡配置的導航清晰度（玩家不只靠顏色也能辨認方位嗎？）
- 確認主線路徑的指標除了顏色，也有用形狀／圖示／聲音提示
- 檢視任何謎題機制的認知負荷，凡是需要同時記住超過 3 個狀態的都要標出來
- 確認關鍵遊戲區域對色盲玩家有足夠的對比
- 輸出：附嚴重程度（BLOCKING / RECOMMENDED / NICE TO HAVE）的無障礙問題清單

等兩個 agent 都回來再往下走。

**Gate**：用 `AskUserQuestion` 呈現 Step 4 的兩份結果。如果 accessibility-specialist 回傳了任何 BLOCKING 的問題，要醒目地標出來，並提供：
- (a) 回頭請 level-designer 和 art-director 重新設計被標出的元素，再進 Step 5
- (b) 記為已知的無障礙缺口，帶著這個問題明確記錄在最終報告裡，繼續進 Step 5

使用者沒有確認任何 BLOCKING 的無障礙問題之前，絕對不准進 Step 5。

### Step 5: QA Planning (qa-tester)
Spawn `qa-tester` agent 來：
- 為主線路徑撰寫測試案例
- 找出邊界與邊緣案例（順序跳過、軟鎖死）
- 為這個區域建立試玩檢查表
- 定義關卡完成的驗收標準

4. **彙整關卡設計文件**，把所有團隊成員的產出合併成關卡設計模板的格式。

orchestrator 已經握有每個 sub-agent 的產出：**自己彙整文件，不要再 spawn 一次 `level-designer`、把所有產出原封不動重送過去。** 第二次 spawn 要付一個全新 agent 的開銷，外加把 orchestrator 手上已有的 context 完整重傳一遍，只為了搬運它本來就握著的文字。彙整成關卡設計模板格式之後，直接用 `AskUserQuestion` 問使用者：「May I write the compiled level design to
`design/levels/[level-name].md`?」核准後再寫。

5. 該次核准之後，**儲存到** `design/levels/[level-name].md`。
   `[level-name]` 是參數轉成的 slug：全小寫、空格換成連字號
   （`forest dungeon` → `forest-dungeon.md`），相鄰區域檢查裡的 `[area-name]` 也用同樣的方式轉 slug。

## File Write Protocol

每個 agent 的產出（敘事文件、測試檢查表）由產出它們的 sub-agent 自己寫，依據的是上面「為什麼這不違反 Collaboration Protocol」所記載的**有界例外**：路徑是你指定的、產物是 `production/`、`docs/` 或 `tests/` 底下的新檔案、而且這個 phase 有 `AskUserQuestion` 把關。在這些範圍內，sub-agent **不會**每次寫入都問；範圍之外就一定要問。**唯一的例外是最後彙整出來的關卡設計文件**：orchestrator 已經握有所有輸入，所以它自己彙整，並在自己的「May I write …?」提示之後（Step 4）親自寫那個檔案，光為了寫 orchestrator 手上已有的文字就重新 spawn 一個 agent，純粹是浪費。

Verdict: **COMPLETE** — level design document produced and all team outputs compiled.
Verdict: **BLOCKED** — one or more agents blocked, or an agent was skipped (`.claude/docs/error-recovery-protocol.md` step 5); partial report produced with unresolved items listed.

## Error Recovery Protocol

**先驗證產物。** 如果回傳約定指定了路徑，在把這個 phase 當成做完之前，先確認該路徑真的存在：**指名的產物不在磁碟上，就是失敗的 phase，不管回覆讀起來多流暢。** agent 可能耗掉整個 phase，回你一段看似合理的開場白，卻什麼都沒寫；這既不是 BLOCKED、也不是錯誤、也不是「無法完成」，所以下面的觸發條件永遠不會被觸發。要叫它繼續，並指明沒達成的約定；context 通常還在。

如果任何 spawn 出去的 agent 回傳 BLOCKED、出錯或無法完成：**立刻揭露，不要越過它所阻擋的依賴項繼續往下走，而且一定要產出部分報告。** 被略過的 agent 那一節要留成一個有名字的缺口，絕對不准用你自己的內容填進去。完整流程：`.claude/docs/error-recovery-protocol.md`。

- 輸入檔案缺失（找不到 story、GDD 不存在）→ 導向建立它的 skill
- ADR 狀態是 Proposed → 不要實作；決定之後，用 `/architecture-decision accept ADR-NNNN` 接受它
- 範圍太大 → 用 `/create-stories` 拆成兩個 story
- ADR 和 story 的指示互相衝突 → 把衝突揭露出來，不要猜

## How to Delegate

Use the `Agent` tool to spawn each team member as a subagent:
- `subagent_type: narrative-director` — Narrative purpose, characters, emotional arc
- `subagent_type: world-builder` — Lore context, environmental storytelling, world rules
- `subagent_type: level-designer` — Spatial layout, pacing, encounters, navigation
- `subagent_type: systems-designer` — Enemy compositions, loot tables, difficulty balance
- `subagent_type: art-director` — Visual theme, color palette, lighting, asset requirements
- `subagent_type: accessibility-specialist` — Navigation clarity, colorblind safety, cognitive load
- `subagent_type: qa-tester` — Test cases, boundary testing, playtest checklist

**Brief each agent — do not dump context.** Read the shared inputs **once** and pass a distilled brief inline: the lines each agent actually needs, never a file path for a document you have already read (an agent handed a path re-reads the whole file). Pass a path only for a document you have not read and only that agent needs.

**End every agent prompt with a return contract:** "Write your full output to `[path]` — that named path is your write authorisation under the bounded exception below, so write it without a separate approval prompt. Return **only** (1) the path written, (2) a ≤5-bullet summary of decisions, (3) any BLOCKED/CONCERNS items, one line each. Do not restate the documents you read." Without it, an agent returns everything it read back into this session.

**Substitute a real path for `[path]`.** Working artifacts go under
`production/levels/[level-name]/`, slugged as in the "Save to" step below. One
file per agent, so the parallel steps never share one:

| Step / agent | Writes to |
|---|---|
| 1 narrative-director | `production/levels/[level-name]/narrative.md` |
| 1 world-builder | `production/levels/[level-name]/lore.md` |
| 1 art-director | `production/levels/[level-name]/visual-direction.md` |
| 2 level-designer | `production/levels/[level-name]/layout.md` |
| 3 systems-designer | `production/levels/[level-name]/systems.md` |
| 4 art-director | `production/levels/[level-name]/production-concepts.md` |
| 4 accessibility-specialist | `production/levels/[level-name]/accessibility.md` |
| 5 qa-tester | `production/qa/test-cases/[level-name]-cases.md` — test cases, edge cases, playtest checklist, acceptance criteria |

These are working drafts; the durable record is the level design document you
compile from them (`design/levels/[level-name].md`).

> **Why this does not violate the Collaboration Protocol.** `CLAUDE.md` requires an agent to ask "May I write this to [filepath]?" before Write/Edit. A subagent spawned here writes **without** asking, and that is a deliberate, bounded exception rather than an oversight — the same call already made for `consistency-check` appending to `active.md`. The exception holds only when all three are true: (1) the path is one **you** named in the prompt, so the user approved the destination when they approved the phase; (2) it is a new artifact under `production/`, `docs/` or `tests/`, never an edit to existing source or config; (3) the phase that produced it is itself gated by an `AskUserQuestion` before the pipeline advances. Outside those three, the agent must ask. **Do not "fix" this by asking per subagent** — a prompt per agent per phase makes an orchestrator unusable, which is why the exception exists.

### Step 1: Narrative + Visual Direction (narrative-director + world-builder + art-director, parallel)

- Identify key characters, dialogue triggers, and lore elements
- Specify emotional arc (how should the player feel entering, during, leaving?)

Spawn the `world-builder` agent to:
- Provide lore context for the area (history, faction presence, ecology)
- Define environmental storytelling opportunities
- Specify any world rules that affect gameplay in this area

Spawn the `level-designer` agent with the full Step 1 output as context:

- Place encounters with difficulty progression
- Design environmental puzzles or navigation challenges

- Specify entry/exit points and connections to adjacent areas

- Specify enemy compositions and encounter formulas
- Define loot tables and reward placement
- Balance difficulty relative to expected player level/gear

Spawn the `art-director` agent with the finalized layout from Step 2:
- Produce location-specific concept specs for key spaces (entrance, key encounter zones, landmarks, exits)
- Specify which art assets are unique to this area vs. shared from the global pool
- Define sight-line and lighting setups per key space (these are now layout-informed, not directional)
- Specify VFX needs that are specific to this area's layout (weather volumes, particles, atmospheric effects)
- Flag any locations where the layout creates visual direction conflicts with the Step 1 targets — surface these as production risks

- Review the level layout for navigation clarity (can players orient themselves without relying on color alone?)
- Check that critical path signposting uses shape/icon/sound cues in addition to color

**First, verify the artifact.** If the return contract named a path, check the

is neither BLOCKED nor an error nor "cannot complete", so the trigger below
never fires. Resume it naming the unmet contract; the context is
usually still there.

If any spawned agent returns BLOCKED, errors, or cannot complete: **surface it
immediately, don't proceed past a dependency it blocks, and always produce a
partial report.** A skipped agent's section stays a named gap — never fill it with content of your own. Full procedure: `.claude/docs/error-recovery-protocol.md`.

Common blockers:
- Input file missing (story not found, GDD absent) → redirect to the skill that creates it

- Scope too large → split into two stories via `/create-stories`
- Conflicting instructions between ADR and story → surface the conflict, do not guess
