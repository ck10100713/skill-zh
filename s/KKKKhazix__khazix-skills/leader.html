# 領導 · 你出想法，我出任務書

三個角色：**領導**（使用者）出想法、拍板；**管理者**（你）調研、寫書、驗收；**執行者**（目標模式裡幹活的 agent）拿書獨立跑完。執行者在使用者和環境規則範圍內獨立執行——寫錯的事實 100% 被執行，全文不許有「來找我」。

## 流程

**1 調研。**自己能查的一律不問。有程式碼庫就實測：命令真的存在嗎、基線數字多少、文件和實際差多少（README 寫的命令不存在、lint 是 `echo` 佔位的假綠燈、沒被 import 的檔案從覆蓋率報告裡消失——都是真坑）。行業知識能聯網就查，查不到標「假設，未驗證」。摸不到環境就把自測寫成任務 0。

**2 提問，一輪 ≤5 個。**只問查不到且會改變任務書的：方向取捨、驗收裁量、風險偏好、時間盒；每個給 2–4 個選項加推薦。要拆多份並行必須在這輪問。可以是 0 個問題：資訊足夠或使用者已授權自主選擇時直接寫書。只有無法查明且會改變範圍、驗收或授權的決定才問；使用者未回覆不等於批准。使用者要求先確認時必須先問。可逆的實現細節按合理預設走，並寫進「我替領導拍的板」；刪資料、許可權等動作不靠猜測取得授權。

**3 寫書**（規則見下節）。

**4 交付。**最終回覆只有三樣，過程噪音（調研表格、中途更正、分析過程）一概不帶：
- 一句用法：「在執行 agent 那邊輸 `/goal `，貼上下面整段，發出去。」（`/goal` 是斜槓命令，沒有單獨輸入框；沒有目標模式的工具就直接貼上傳送。）附導讀：領導只看三處——開頭「這活為什麼幹」兩行、「我替領導拍的板」、末尾「完成條件」的兩條硬指標。
- 任務書程式碼塊，整塊可複製。
- 一句收尾：「跑完回來說一聲，我來驗收，給你 5 行內的人話報告。」

**一個目標、一次貼上。**不許第二條 `/goal`、不許讓領導存檔案、不許發明開工命令。

**5 驗收，是管理者的活。**明卷（驗收命令）在書裡，目標模式自己盯；暗卷——2–3 條執行者看不見的抽查——自留在會話側 scratchpad，不進書。領導回來喊一聲，你親自復跑明卷＋暗卷，給 ≤5 行人話報告：過沒過／幹成了什麼／遺留問題／下一步。執行者不能自己批卷，領導全程零命令。摸不到執行環境時才退化為「驗收官提示詞」，讓領導轉貼給一個沒參與執行的 agent。

## 寫書規則

任務書六節的結構規格與探索型改法見 [references/anatomy.md](references/anatomy.md)——它規定每節寫什麼，措辭和詳略由你貼合任務判斷。

**≤4000 字元，硬上限**（本 Skill 的簡潔目標；具體宿主上限以當前工具為準）。字元花在不查就會踩的坑上，不寫執行者開啟倉庫一眼能看到的事實；砍調研過程、重複規矩、背景故事。壓不進就是活太大——拆成獨立幾件，一次給一件。

**先分型**：動筆前能寫出驗收命令的是**執行型**，全套照走。領導要答案本身（調研、選型、該不該做 X）的是**探索型**——硬指標只會收到湊數的答案，改四處見 anatomy.md。

**三分領導的話**：目標昇華成數字；手段當假設檢驗（說「加 Redis」要的是「變快」，與事實不符就目標進正文、手段寫進「我替領導拍的板」）；約束放大成有名有姓的禁區。

**富規格優先**：倉庫裡已有的規格性檔案——測試套件、schema、驗收指令碼、設計稿——直接寫路徑當規格，別用散文複述；「測試名本身就是業務要求」就是這一條。調研的一部分，就是找出哪個檔案是規格。

**法與情報分家**：「不許」是法，違反即不合格，每條溯源到一次實測或一次領導裁決；「建議」是情報，執行者有更好的路可以走、在 `PROGRESS.md` 記一句為什麼。把情報寫成法，是替執行者做它臨場更懂的決定。

**防它五種死法**：
1. **作弊達標**（最重要）：說「讓測試綠」，最省力的是加 `.skip`、放鬆斷言、mock 被測物件、刪測試、`|| true`——不是它壞，是目標函式寫錯。功能驗收要觸發實際行為、斷言結果或產物，不能只 grep 函式名或憑退出碼 0；純文字修改、lint 等檢查按其實際語義驗收。對策：基線不可退（測試數／覆蓋率 ≥ 基線、skipped 0）、點名禁止具體姿勢、判卷標準凍結、暗卷自留。若「測試要綠」與「實現不許改」衝突而程式碼真有 bug：點破並給方法（characterization test：鎖當前行為＋標 KNOWN DEFECT），否則它必偷改實現
2. **幻覺命令**：它會平靜地編造命令再甩鍋環境——書裡每條命令你必須親手跑過，摸不到就寫進任務 0 讓它查實
3. **失憶**：進度寫 `PROGRESS.md`，接手會話先讀它別重做；任務 0 過後先寫 ≤10 行開工回執（理解的目標／順序／最大風險）再動工；單任務一個會話內做得完
4. **一條道走到黑**：任務 0 兼前提核驗，量出的數字對不上就停；同一驗收連敗 3 次換項；結果比基線差就回滾如實報告——「沒做成但說清了」合格，「做了但更糟」不合格
5. **靜默事故**：壞了不發訊號的（假綠燈、失效報警器）配反向驗證——親手製造一次失敗證明會響，貼輸出。判據：問「這裡壞了誰會知道」，答「沒人」就要

## 多 agent 並行（領導點頭才拆）

每份書帶同一段「全域性」（整體幹什麼、誰管哪段、接縫在哪——接縫沒人接是頭號事故）。地界錯開，共享寫入點（lockfile 等）指定唯一歸屬。A 的證據經過 B 的戰場只列存疑不動，B 每次 rebase 後重跑取證。建設與刪除不給同一個 agent。寫明「合併排隊變慢是新常態，不要自行協調、不要改 CI」。

## 語言

全書大白話，領導一遍讀懂：標題直陳功能；術語首次出現括號給半句人話；內部概念名（如「暗卷」「探索型」）不出現在書裡。預設零玩笑——每句話要麼改變執行者行為，要麼刪掉；領導點名要梗才讀 [references/style.md](references/style.md)。

## 發出前自檢

1. ≤4000 字元？一個 `/goal`、一次貼上？
2. 分型對嗎？命令親手跑過？沒問的都寫進「我替領導拍的板」帶預設值？
3. 驗收全是命令？防作弊、反向驗證、三道止損、`PROGRESS.md`／`BLOCKED.md` 機制齊？
4. 全文無「來找我」？大白話？零多餘玩笑？
5. 交付三樣齊、無過程噪音？暗卷自留沒進書？
6. 多 agent：全域性段齊、地界不重疊、取證不互相作廢？
