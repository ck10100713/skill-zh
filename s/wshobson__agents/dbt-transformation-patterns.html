# dbt 轉換模式

可用於 production 的 dbt（data build tool）模式，包含 model 組織、測試策略、文件與 incremental 處理。

## 什麼時候用這個 Skill

- 用 dbt 建立資料轉換 pipeline
- 把 model 整理成 staging、intermediate、marts 三層
- 實作資料品質測試
- 為大型資料集建立 incremental model
- 為資料模型與 lineage 寫文件
- 設定 dbt 專案結構

## 核心概念

### 1. Model 分層（Medallion Architecture）

```
sources/          原始資料定義
    ↓
staging/          與來源 1:1，輕度清理
    ↓
intermediate/     商業邏輯、join、彙總
    ↓
marts/            最終分析用資料表
```

### 2. 命名慣例

| 層級         | 前綴           | 範例                          |
| ------------ | -------------- | ----------------------------- |
| Staging      | `stg_`         | `stg_stripe__payments`        |
| Intermediate | `int_`         | `int_payments_pivoted`        |
| Marts        | `dim_`, `fct_` | `dim_customers`, `fct_orders` |

## 快速開始

```yaml
# dbt_project.yml
name: "analytics"
version: "1.0.0"
profile: "analytics"

model-paths: ["models"]
analysis-paths: ["analyses"]
test-paths: ["tests"]
seed-paths: ["seeds"]
macro-paths: ["macros"]

vars:
  start_date: "2020-01-01"

models:
  analytics:
    staging:
      +materialized: view
      +schema: staging
    intermediate:
      +materialized: ephemeral
    marts:
      +materialized: table
      +schema: analytics
```

## 最佳實務

### 該做的

- **使用 staging 層**：資料只清一次，到處都能用
- **積極做測試**：not null、unique、relationships
- **每樣東西都寫文件**：欄位描述、model 描述
- **使用 incremental**：資料表超過 100 萬筆時
- **版本控制**：dbt 專案放在 Git

### 不該做的

- **不要跳過 staging**：從 Raw 直接做到 mart 是技術債
- **不要寫死日期**：用 `{{ var('start_date') }}`
- **不要重複邏輯**：抽成 macro
- **不要在 prod 測試**：用 dev target
- **不要忽略 freshness**：要監控來源資料

# dbt Transformation Patterns

Production-ready patterns for dbt (data build tool) including model organization, testing strategies, documentation, and incremental processing.

## When to Use This Skill

- Building data transformation pipelines with dbt
- Organizing models into staging, intermediate, and marts layers
- Implementing data quality tests
- Creating incremental models for large datasets
- Documenting data models and lineage
- Setting up dbt project structure

## Core Concepts

### 1. Model Layers (Medallion Architecture)

```
sources/          Raw data definitions
    ↓
staging/          1:1 with source, light cleaning
    ↓
intermediate/     Business logic, joins, aggregations
    ↓
marts/            Final analytics tables
```

### 2. Naming Conventions

| Layer        | Prefix         | Example                       |
| ------------ | -------------- | ----------------------------- |
| Staging      | `stg_`         | `stg_stripe__payments`        |
| Intermediate | `int_`         | `int_payments_pivoted`        |
| Marts        | `dim_`, `fct_` | `dim_customers`, `fct_orders` |

## Best Practices

### Do's

- **Use staging layer** - Clean data once, use everywhere
- **Test aggressively** - Not null, unique, relationships
- **Document everything** - Column descriptions, model descriptions
- **Use incremental** - For tables > 1M rows
- **Version control** - dbt project in Git

### Don'ts

- **Don't skip staging** - Raw → mart is tech debt
- **Don't hardcode dates** - Use `{{ var('start_date') }}`
- **Don't repeat logic** - Extract to macros
- **Don't test in prod** - Use dev target
- **Don't ignore freshness** - Monitor source data
