# /legal-response -- 依範本產生回覆

> 如果看到不認識的佔位符，或需要確認目前連了哪些工具，請看 [CONNECTORS.md](../../CONNECTORS.md)。

使用已設定的範本，針對常見的法務詢問產生回覆。依具體細節客製化回覆內容，並納入升級觸發條件，處理不該使用範本回覆的情況。

**重要**：這個指令協助處理法務工作流程，但不提供法律意見。產生的回覆在寄出前應該由合格的法務專業人員審閱，受規範的通訊尤其如此。

## 呼叫方式

```
/legal-response [inquiry-type]
```

常見的詢問類型：
- `dsr` 或 `data-subject-request` -- 資料當事人的查閱/刪除/更正請求
- `hold` 或 `discovery-hold` -- 訴訟保全通知
- `vendor` 或 `vendor-question` -- 供應商的法務問題
- `nda` 或 `nda-request` -- 業務團隊的 NDA 請求
- `privacy` 或 `privacy-inquiry` -- 隱私相關問題
- `subpoena` -- 傳票或法律程序的回覆
- `insurance` -- 保險理賠通知
- `custom` -- 使用自訂範本

如果沒有提供詢問類型，就問使用者需要哪一種回覆，並列出可用的類別。

## 工作流程

### Step 1：辨識詢問類型

接受使用者給的詢問類型。如果類型不明確，就列出可用的類別並請使用者釐清。

### Step 2：載入範本

在本機設定（例如 `legal.local.md` 或範本資料夾）裡找範本。

**如果有設定範本：**
- 載入適合該詢問類型的範本
- 找出必要的變數（收件人姓名、日期、具體細節）

**如果沒有設定範本：**
- 告知使用者找不到這個詢問類型的範本
- 提議協助建立範本（見下方的範本建立指南）
- 依詢問類型提供一個合理的預設回覆結構

### Step 3：檢查升級觸發條件

產生任何回覆之前，先評估這個情況有沒有不該用範本回覆的特徵。

#### 通用升級觸發條件（適用於所有類別）
- 事件涉及潛在的訴訟或監管調查
- 詢問來自監管機關、政府機關或執法單位
- 回覆可能造成有約束力的法律承諾或權利拋棄
- 事件涉及潛在的刑事責任
- 涉及或可能引起媒體關注
- 情況前所未見（團隊沒處理過）
- 涉及多個司法管轄區，且要求互相衝突
- 事件涉及高階主管或董事會成員

#### 資料當事人請求的升級觸發條件
- 請求涉及未成年人的資料，或來自未成年人 / 代表未成年人
- 請求來自監管機關（不是個人）
- 請求涉及受訴訟保全約束的資料
- 請求人是現任或前任員工，且有進行中的爭議或人資案件
- 請求範圍異常廣泛，或看起來像是撒網式的探查
- 請求涉及在有特殊要求的司法管轄區處理的資料
- 請求涉及特殊類別資料（健康、生物辨識、基因）

#### 訴訟保全的升級觸發條件
- 事件涉及潛在的刑事責任
- 保全範圍不清楚、有爭議，或可能過於寬泛
- 對於某些資料是否在範圍內有疑問
- 同一或相關事件已有先前的保全
- 保全可能對持續中的業務營運造成重大影響
- 保全與監管要求的刪除義務衝突
- 保管人（custodian）反對保全範圍

#### 供應商問題的升級觸發條件
- 問題涉及爭議或潛在的違約
- 供應商威脅提告或終止合作
- 問題涉及法規遵循（不只是合約條款）
- 回覆可能造成有約束力的承諾或權利拋棄
- 回覆可能影響進行中的協商

#### NDA 請求的升級觸發條件
- 對方是競爭對手
- NDA 涉及政府機密資訊
- 業務脈絡顯示這份 NDA 是為了潛在的併購交易
- 請求涉及不尋常的主題（AI 訓練資料、生物辨識資料等）

#### 傳票 / 法律程序的升級觸發條件
- **一律需要律師審閱**（範本只是起點）
- 發現有特權（privilege）問題
- 涉及第三方資料
- 跨境提交的問題
- 不合理的時程

**偵測到升級觸發條件時：**
1. **停下來**：不要產生範本回覆
2. **警示**：告知使用者偵測到升級觸發條件
3. **說明**：描述偵測到哪個觸發條件，以及為什麼重要
4. **建議**：建議適當的升級途徑（資深律師、外部律師、特定團隊成員）
5. **提供**：提供一份供律師審閱的草稿（明確標示為「DRAFT - FOR COUNSEL REVIEW ONLY」），而不是最終回覆

### Step 4：收集具體細節

向使用者詢問客製化回覆所需的細節：

**資料當事人請求：**
- 請求人姓名和聯絡資訊
- 請求類型（查閱、刪除、更正、可攜、退出）
- 涉及哪些資料
- 適用的法規（GDPR、CCPA、CPRA、其他）
- 回覆期限

**訴訟保全：**
- 案件名稱和參考編號
- 保管人（誰需要保全）
- 保全範圍（日期範圍、資料類型、系統）
- 外部律師的聯絡方式
- 生效日期

**供應商問題：**
- 供應商名稱
- 參照的合約（如適用）
- 要回覆的具體問題
- 相關的合約條款

**NDA 請求：**
- 提出請求的業務團隊和聯絡人
- 對方名稱
- NDA 的目的
- 雙向或單向
- 任何特殊要求

### Step 5：產生回覆

把收集到的細節填進範本。確保回覆：
- 語氣適當（專業、清楚，對業務讀者不要過度法律腔）
- 包含該回覆類型所需的全部法律要素
- 引用具體的日期、期限和義務
- 給收件人清楚的下一步
- 包含適當的免責聲明或但書

寄出前，先把草稿回覆呈現給使用者審閱。

#### 客製化準則

**必要的客製化**：每一份範本回覆都一定要客製化這些：
- 正確的姓名、日期和參考編號
- 這個情況的具體事實
- 適用的司法管轄區和法規
- 依收到詢問的時間算出的正確回覆期限
- 適當的簽名區塊和聯絡資訊

**語氣調整**：依下列因素調整語氣：
- **對象**：內部或外部、業務或法務、個人或監管機關
- **關係**：新的對方、既有的夥伴，還是對立方
- **敏感度**：例行詢問、有爭議的事件，還是監管調查
- **急迫性**：標準時程，還是需要加速回覆

**依司法管轄區的調整：**
- 確認引用的法規適用於請求人所在的司法管轄區
- 調整時程以符合適用的法律
- 納入該司法管轄區特有的權利資訊
- 使用適合該司法管轄區的法律術語

### Step 6：建立範本（如果沒有現成範本）

如果使用者想建立新範本，就帶他走一遍範本建立指南（見下方），並把完成的範本呈現給他審閱。建議使用者把核准的範本存到本機設定，供日後使用。

## 回覆類別

### 1. 資料當事人請求（DSR）

**子類別**：
- 確認收到
- 要求身分驗證
- 履行回覆（查閱、刪除、更正）
- 附說明的部分拒絕
- 附說明的完全拒絕
- 延期通知

**範本的關鍵要素**：
- 引用適用的法規（GDPR、CCPA 等）
- 具體的回覆時程
- 身分驗證要求
- 資料當事人的權利（包括向主管機關申訴的權利）
- 後續聯絡資訊

**範本結構範例**：
```
Subject: 您的資料 [查閱/刪除/更正] 請求 - 參考編號 {{request_id}}

{{requester_name}} 您好，

我們已收到您於 {{request_date}} 依據 [適用法規] 提出的 [查閱/刪除/更正] 您個人資料的請求。

[確認收到 / 驗證請求 / 履行細節 / 拒絕依據]

我們將於 {{response_deadline}} 前做出實質回覆。

[聯絡資訊]
[權利資訊]
```

### 2. 訴訟保全（Discovery Holds / Litigation Holds）

**子類別**：
- 給保管人的初始保全通知
- 保全提醒 / 定期重新確認
- 保全修改（範圍變更）
- 保全解除

**範本的關鍵要素**：
- 案件名稱和參考編號
- 清楚的保全義務
- 保全範圍（日期範圍、資料類型、系統、通訊類型）
- 禁止毀滅證據
- 問題聯絡窗口
- 要求回覆確認

**範本結構範例**：
```
Subject: 法律保全通知 - {{matter_name}} - 需要採取行動

PRIVILEGED AND CONFIDENTIAL
ATTORNEY-CLIENT COMMUNICATION

{{custodian_name}} 您好，

您收到這份通知，是因為您可能持有與上述事件相關的文件、通訊或資料。

保全義務：
即日起，您必須保全所有與下列事項相關的文件和電子儲存資訊（ESI）：
- 主題事項：{{hold_scope}}
- 日期範圍：{{start_date}} 至今
- 文件類型：{{document_types}}

請勿刪除、銷毀、修改或丟棄任何可能相關的資料。

[針對系統、email、聊天、本機檔案的具體指示]

請於 {{acknowledgment_deadline}} 前回覆確認收到這份通知。

如有任何問題，請聯絡 {{legal_contact}}。
```

### 3. 隱私詢問

**子類別**：
- Cookie/追蹤詢問的回覆
- 隱私政策問題
- 資料分享做法的詢問
- 兒童資料的詢問
- 跨境傳輸的問題

**範本的關鍵要素**：
- 引用組織的隱私聲明
- 依目前做法給出具體答覆
- 連到相關的隱私文件
- 隱私團隊的聯絡資訊

### 4. 供應商的法務問題

**子類別**：
- 合約狀態詢問的回覆
- 修訂請求的回覆
- 合規認證請求
- 稽核請求的回覆
- 保險證明請求

**範本的關鍵要素**：
- 引用適用的合約
- 針對供應商問題的具體回覆
- 任何必要的但書或限制
- 下一步和時程

### 5. NDA 請求

**子類別**：
- 寄出組織的標準格式 NDA
- 接受對方的 NDA（附修訂標記）
- 附說明地婉拒 NDA 請求
- NDA 續約或延期

**範本的關鍵要素**：
- NDA 的目的
- 標準條款摘要
- 簽署說明
- 時程預期

### 6. 傳票 / 法律程序

**子類別**：
- 確認收到
- 異議函
- 延期請求
- 配合的附函

**範本的關鍵要素**：
- 案件參考和司法管轄區
- 具體的異議（如有）
- 保全確認
- 配合的時程
- 特權清單的參照（如適用）

**重要提醒**：傳票的回覆幾乎都需要針對個案由律師審閱。範本只是起始架構，不是最終回覆。

### 7. 保險通知

**子類別**：
- 初始理賠通知
- 補充資訊
- 保留權利的回覆

**範本的關鍵要素**：
- 保單號碼和承保期間
- 事件或事故的描述
- 事件時間軸
- 要求確認的承保範圍

## 範本管理方法

### 範本的組織

範本應該依類別組織，並維護在團隊的本機設定裡。每份範本都應該包含：

1. **類別**：範本處理的詢問類型
2. **範本名稱**：一個描述性的識別名稱
3. **使用情境**：什麼時候適合用這份範本
4. **升級觸發條件**：什麼時候不該用這份範本
5. **必要變數**：每次使用都必須客製化的資訊
6. **範本本文**：帶有變數佔位符的回覆文字
7. **後續動作**：寄出回覆後的標準步驟
8. **最後審閱日期**：範本最後一次確認正確性的時間

### 範本生命週期

1. **建立**：依最佳實務和團隊意見擬範本
2. **審閱**：法務團隊審閱並核准範本內容
3. **發布**：連同 metadata 加進範本庫
4. **使用**：用範本產生回覆
5. **回饋**：追蹤範本在使用時被修改的情況，找出可改進的地方
6. **更新**：法律、政策或最佳實務改變時修訂範本
7. **淘汰**：封存不再適用的範本

## 範本建立指南

協助使用者建立新範本時：

### 1. 定義使用情境
- 這個範本處理哪種詢問？
- 多常出現？
- 一般的讀者是誰？
- 一般的急迫程度如何？

### 2. 找出必要要素
- 每一份回覆都必須包含哪些資訊？
- 適用哪些法規要求？
- 哪些組織政策管轄這類回覆？

### 3. 定義變數
- 每次使用有什麼會變？（姓名、日期、具體細節）
- 什麼保持不變？（法律要求、標準用語）
- 使用清楚的變數名稱：`{{requester_name}}`、`{{response_deadline}}`、`{{matter_reference}}`

### 4. 擬範本
- 用清楚、專業的語言寫
- 對業務讀者避免不必要的法律行話
- 包含所有法律上要求的要素
- 為所有會變動的內容加上佔位符
- 如果是 email 用，要加上主旨行範本

### 5. 定義升級觸發條件
- 哪些情況不該用這份範本？
- 哪些特徵代表這件事需要個別處理？
- 要具體：模糊的觸發條件沒有用

### 6. 加上 Metadata
- 範本名稱和類別
- 版本號和最後審閱日期
- 作者和核准人
- 後續動作檢查清單

### 範本格式

```markdown
## Template: {{template_name}}
**Category**: {{category}}
**Version**: {{version}} | **Last Reviewed**: {{date}}
**Approved By**: {{approver}}

### Use When
- [條件 1]
- [條件 2]

### Do NOT Use When (Escalation Triggers)
- [觸發條件 1]
- [觸發條件 2]

### Variables
| Variable | Description | Example |
|---|---|---|
| {{var1}} | [是什麼] | [範例值] |
| {{var2}} | [是什麼] | [範例值] |

### Subject Line
[含 {{variables}} 的主旨範本]

### Body
[含 {{variables}} 的回覆本文]

### Follow-Up Actions
1. [動作 1]
2. [動作 2]

### Notes
[給這份範本使用者的任何特殊說明]
```

## 輸出格式

```
## Generated Response: [詢問類型]

**To**: [收件人]
**Subject**: [主旨行]

---

[回覆本文]

---

### Escalation Check
[確認沒有偵測到升級觸發條件，或是標出被觸發的條件並附上建議]

### Follow-Up Actions
1. [寄出後的動作]
2. [要設定的行事曆提醒]
3. [追蹤或記錄的要求]
```

## 備註

- 建議寄出之前，一定要先把草稿回覆呈現給使用者審閱
- 如果透過 MCP 連上 email，就提議把回覆建立成 email 草稿
- 追蹤回覆期限，並提議設定行事曆提醒
- 受規範的回覆（DSR、傳票），一定要註明適用的期限和法規要求
- 範本應該是活的文件；使用者修改了範本回覆時，建議更新範本，讓範本能隨時間改進
