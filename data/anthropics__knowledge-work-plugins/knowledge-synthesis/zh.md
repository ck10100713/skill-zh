# Knowledge Synthesis

企業搜尋的最後一哩路。拿多個來源的原始結果，產出連貫、可信的答案。

## 目標

把這個：
```
~~chat result: "Sarah said in #eng: 'let's go with REST, GraphQL is overkill for our use case'"
~~email result: "Subject: API Decision — Sarah's email confirming REST approach with rationale"
~~cloud storage result: "API Design Doc v3 — updated section 2 to reflect REST decision"
~~project tracker result: "Task: Finalize API approach — marked complete by Sarah"
```

變成這個：
```
團隊決定 API 改版用 REST，不用 GraphQL。Sarah 做了這個決定，
她說 GraphQL 對目前的使用情境來說太大材小用。這件事週二在 #engineering
討論過，週三用 email 確認，設計文件也已經更新來反映這個決定。相關的 ~~project tracker 任務已標為完成。

Sources:
- ~~chat: #engineering thread (Jan 14)
- ~~email: "API Decision" from Sarah (Jan 15)
- ~~cloud storage: "API Design Doc v3" (updated Jan 15)
- ~~project tracker: "Finalize API approach" (completed Jan 15)
```

## 去除重複

### 跨來源去重

同樣的資訊常常出現在多個地方。要辨識並合併重複：

**代表結果在講同一件事的訊號：**
- 相同或非常相似的文字內容
- 相同的作者/寄件者
- 時間戳落在短時間內（同一天或相鄰的日子）
- 提到同一個實體（專案名稱、文件、決定）
- 一個來源引用另一個來源（「as discussed in ~~chat」、「per the email」、「see the doc」）

**怎麼合併：**
- 合併成單一敘述項目
- 引用它出現過的所有來源
- 以最完整的版本當主要文字
- 加上每個來源獨有的細節

### 去重的優先順序

同樣的資訊存在於多個來源時，優先選：
```
1. 最完整的版本（脈絡最齊全）
2. 最權威的來源（正式文件 > 聊天）
3. 最新的版本（持續演變的資訊以最新更新為準）
```

### 不該去重的情況

下列情況要保留成獨立項目：
- 討論同一個主題，但結論不同
- 不同的人表達不同的觀點
- 資訊在各來源之間有實質演變（決定的 v1 對比 v2）
- 代表不同的時間段

## 引用與來源標註

整合後的答案裡，每一個主張都必須能追溯到來源。

### 標註格式

直接引用時用行內標註：
```
Sarah 在週三的 email 裡確認了 REST 的做法。
設計文件也已更新來反映這點（~~cloud storage: "API Design Doc v3"）。
```

最後附來源清單，求完整：
```
Sources:
- ~~chat: #engineering discussion (Jan 14) — initial decision thread
- ~~email: "API Decision" from Sarah Chen (Jan 15) — formal confirmation
- ~~cloud storage: "API Design Doc v3" last modified Jan 15 — updated specification
```

### 標註規則

- 一定要寫出來源類型（~~chat、~~email、~~cloud storage 等）
- 要寫出具體位置（頻道、資料夾、討論串）
- 要寫出日期或相對時間
- 相關時要寫出作者
- 有的話要寫出文件或討論串的標題
- ~~chat 要註明頻道名稱
- ~~email 要註明主旨和寄件者
- ~~cloud storage 要註明文件標題

## 信心等級

不是所有結果都一樣可信。依下列因素評估信心：

### 新鮮度

| 時間 | 對信心的影響 |
|---------|------------------|
| 今天 / 昨天 | 對現況的信心高 |
| 本週 | 信心不錯 |
| 本月 | 中等，事情可能已經變了 |
| 超過一個月 | 信心較低，標記為可能已過時 |

狀態類的查詢，要重重加權新鮮度。政策或事實類的查詢，新鮮度比較沒那麼重要。

### 權威性

| 來源類型 | 權威等級 |
|-------------|----------------|
| 正式 wiki / 知識庫 | 最高：有人策展、有人維護 |
| 共用文件（最終版） | 高：刻意發布的 |
| Email 公告 | 高：正式溝通 |
| 會議記錄 | 中高：可能不完整 |
| 聊天訊息（討論串的結論） | 中：不正式，但是即時的 |
| 聊天訊息（討論串進行中） | 較低：可能不代表最終立場 |
| 草稿文件 | 低：尚未定稿 |
| 任務留言 | 看情況：取決於留言者 |

### 表達信心

信心高時（多個新鮮且權威的來源一致）：
```
團隊決定 API 改版用 REST。[直接陳述]
```

信心中等時（單一來源，或有點舊）：
```
根據上個月在 #engineering 的討論，團隊傾向於
API 改版用 REST。從那之後可能已經有變化。
```

信心低時（資料舊、來源不正式，或訊號互相矛盾）：
```
我在 ~~chat 找到三個月前一段關於 API 遷移的討論，
但找不到正式的決定文件。這份資訊
可能已經過時。你可能想跟團隊確認目前的狀況。
```

### 矛盾的資訊

來源互相矛盾時：
```
我找到關於 API 做法互相矛盾的資訊：
- 1 月 10 日 ~~chat 的討論傾向 GraphQL
- 但 Sarah 在 1 月 15 日的 email 確認了 REST
- 設計文件（1 月 15 日更新）反映的是 REST

最新的來源顯示最終決定是 REST，
但較早的 ~~chat 討論一開始探討的是 GraphQL。
```

一定要把矛盾攤出來，不要默默挑一個版本。

## 摘要策略

### 結果少的時候（1 到 5 筆）

每筆結果連同脈絡一起呈現。不需要摘要，把全部都給使用者：
```
[從結果整合出來的直接答案]

[來源 1 的細節]
[來源 2 的細節]

Sources: [完整標註]
```

### 結果中等的時候（5 到 15 筆）

依主題分組，並摘要每一組：
```
[整體答案]

主題 1：[相關結果的摘要]
主題 2：[相關結果的摘要]

Key sources: [最相關的前 3 到 5 個來源]
Full results: 在 [來源] 共找到 [數量] 筆
```

### 結果很多的時候（15 筆以上）

提供高層次的整合，並讓人可以再往下挖：
```
[根據最相關結果得出的整體答案]

Summary:
- [重點發現 1]（有 N 個來源支持）
- [重點發現 2]（有 N 個來源支持）
- [重點發現 3]（有 N 個來源支持）

Top sources:
- [最權威/最相關的來源]
- [第二相關的]
- [第三相關的]

在 [來源清單] 共找到 [總數] 筆結果。
要我深入看哪個特定面向嗎？
```

### 摘要規則

- 先講答案，不是搜尋過程
- 不要列出原始結果，要把它們整合成敘述
- 把來自不同來源的相關項目放在一起
- 保留重要的細微差異和但書
- 給足夠的細節，讓使用者能決定要不要再深入
- 結果很多時，一定要提議提供更多細節

## 整合工作流程

```
[所有來源的原始結果]
          ↓
[1. 去重：合併不同來源的相同資訊]
          ↓
[2. 分群：依主題把相關結果分組]
          ↓
[3. 排序：依與查詢的相關性排列各群與各項目]
          ↓
[4. 評估信心：新鮮度 × 權威性 × 一致性]
          ↓
[5. 整合：產出附標註的敘述性答案]
          ↓
[6. 格式化：依結果數量選擇適當的細節程度]
          ↓
[附來源的連貫答案]
```

## 反模式

**不要：**
- 一個來源一個來源地列結果（「From ~~chat: ... From ~~email: ... From ~~cloud storage: ...」）
- 只因為符合某個關鍵字就放進不相關的結果
- 把答案埋在方法論說明底下
- 呈現互相矛盾的資訊卻沒標示矛盾
- 省略來源標註
- 用跟有充分佐證的事實一樣的信心，呈現不確定的資訊
- 摘要得太狠，把有用的細節都丟了

**要：**
- 先講答案
- 依主題分組，不是依來源
- 適當時標示信心等級
- 明確攤出矛盾
- 每個主張都標明來源
- 結果很多時，提議再深入
