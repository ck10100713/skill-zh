  拆分。依重要性排序，每個發現都用白話解釋。一次性報告，
  不改任何東西。用於「audit this codebase」、「review the whole repo」、
  「find bloat」、「what can I delete」、/ponytail-audit。

像一個剛接手 repo、壞掉時會被叫起來處理的資深工程師那樣，
稽核整個 repo。重要性順序：正確、安全、扛得住
負載、有測試、快、精簡。精簡仍然重要：每多一行，之後都要有人讀、
測試、修。這是使用者要求的報告，所以要完整給出。

## 1. 先畫地圖

- 稽核使用者指名的範圍：資料夾、套件，或整個 repo。
  沒指名就是整個 repo。
- 讀 README、deploy 和 build 設定、相依套件清單、
  進入點（main、routes、handlers、jobs、CLI 指令）和測試。
- 找出預期的負載：是一個人跑腳本，還是很多使用者和
  行程同時在用。以此判斷規模，並說明你假設的是哪種負載。
- 把主要流程從頭追到尾：資料從哪裡進來、存了什麼、
  又送出什麼。這些路徑要完整讀過：使用者的輸入、金流、驗證、
  資料寫入、背景工作、行程之間共用的任何東西。
- repo 很大：深入看出錯代價最高的地方，不要一個檔案一個檔案看。要說明
  哪些部分你沒讀。

## 2. 要找什麼

1. **Bug：** 結果錯誤、崩潰、漏掉的邊界情況（空值、零、最後一項、
   四捨五入、時區）、呼叫端和函式回傳值對不上、
   同一條規則在兩個地方套用得不一樣。
2. **風險：** 安全漏洞（injection、弱隨機性、程式碼裡的密鑰、
   沒檢查使用者的輸入）、資料遺失（錯誤被吞掉、寫入
   順序錯誤、沒有 transaction）。
3. **規模：** 一個使用者沒問題，很多使用者就錯：先檢查再寫入的 race、
   每個行程都做同一份工作、只增不減的記憶體或清單、每個項目
   一個 query、大量輸入下的 O(n^2)、本來應該共用卻是各行程自己持有的狀態。
4. **缺少測試：** 高風險的邏輯（分支、parser、金流、安全、資料
   寫入），沒有任何一個在它壞掉時會失敗的測試。要一個好測試，不是追求覆蓋率。
5. **速度：** 大幅變慢是問題。小幅改善（熱迴圈裡重複的工作）
   是建議；有些軟體連每一毫秒都計較。
6. **精簡：** 不該存在或該更小的程式碼。
   - delete：死碼、沒用到的選項、旗標和設定、投機性的功能
   - reuse：兩個做同一件事的 helper（留一個，指出是哪條路徑）
   - stdlib / native：標準函式庫或平台本來就做得到；
     相依套件做的事，幾行程式碼或平台就做得到
   - yagni：只有一個實作的介面、只有一個產品的 factory、
     只是把呼叫轉傳的 wrapper
   - merge：必須一起改的近乎複製貼上的程式碼
   - split：一個函式或類別做了好幾件不相關的工作，所以
     難讀也難測。要依工作拆，絕對不要依行數拆，也絕對不要拆成
     只為了讓函式變短而存在的 helper。

## 3. 回報之前先檢查

- 每個發現都要有具體的案例：「這個輸入或情境會導致這個
  錯誤的結果」。沒有案例，就不算發現。
- 在說某段程式碼沒用到之前，先在整棵樹 grep 它，包括測試、
  fixture、設定，以及字串或動態參照。
- 標了 `shortcut:`（或較舊的 `ponytail:`）註解並寫明限制的捷徑，是一個
  決定，不是發現，除非預期的負載已經超過那個限制。
- 提出能運作的最小修法。偏好刪程式碼的修法。絕對不要
  加問題不需要的分層、框架或設定。
- 不要個人品味的風格意見，不要「建議考慮」，不要模糊的擔憂。

## 4. 輸出

用非常簡單的英文：短句、日常用字。第一次用到技術
術語時要解釋。讀的人可能從來沒看過這份程式碼。

開頭先寫 `What this repo does:`，兩三句話，再寫你假設的
負載。

然後把發現分成三組，最重要的放最前面，空的組別跳過：
- **Must fix：** bug、安全、資料遺失、在預期負載下會壞掉。
- **Should fix：** 沒有測試的高風險程式碼、真正的慢、重複、
  一個函式混了好幾種工作、不該存在的程式碼。
- **Nice to have：** 小幅提速、更短的寫法。

發現要跨組連續編號，這樣使用者可以說「修 2 和 5」。
最多 20 個發現；如果你省略了比較小的，要說省略了幾個。
每個發現都要有完整的四個部分，每部分一兩句短句：

2. **訂單落在錯的日期**（`billing/close_day.py:L40-52`）
   - **這是什麼：** 這個工作在午夜結算當天，並對當天所有訂單收費。
   - **問題：** 它從伺服器時鐘取得「今天」，而伺服器用的是 UTC。柏林時間
     00:30 下的訂單，會被算到前一天。
   - **修法：** 在商店的時區裡，只算一次日期：
     `datetime.now(ZoneInfo("Europe/Berlin")).date()`。一行，其他都不用動。
   - **如果不修：** 晚下的訂單會顯示錯的日期，會計得手動修正。

結尾要有：
- `Verdict:` 一行：健康，或是該先修什麼。
- `Lean: -<N> lines, -<M> dependencies possible.`，有精簡類的發現時才寫。
- `Not checked:` 你沒讀或沒辦法執行的部分。

什麼都沒發現：寫 `What this repo does:`，然後寫 `Healthy. Nothing to fix.`，
再加一行說明你檢查了什麼。

一次性報告，不改任何程式碼。
