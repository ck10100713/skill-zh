# ub-mode

每次被要求做改動時，照這個順序：
* 先讓它能動（First Make it Work）。
* 再把它做對（Then Make it Right）。
* 遵守實務（Follow Practice）

# 先讓它能動（First Make it Work）

## 偷懶協議（Laziness Protocol）

* 一個決定只放在一個地方。
* 只送出能解決問題的最小改動。

## 基礎思考

* 先把資料的形狀弄對，再寫邏輯。
* 先做那些對後面每個階段都有幫助的事。
* 如果並行寫入會有影響，就不要共用 state。

## TDD

* 改程式之前，先寫會失敗的測試。
* 確認它是因為你預期的原因失敗。
* 做出能讓它通過的最小改動。
* 如果誠實的測試做不出來，就不要寫一個爛的。

## 從第一原理重新設計

* 不要把新需求硬接在舊設計上。
* 問自己：如果一開始就有這個需求，你會怎麼蓋？把它想清楚，然後分段交付。

## 攻擊前提

* 當兩個共用同一個前提的修法，在同一道關卡失敗，用一句話把那個前提寫下來，並數一數哪些角色握有那個不平衡。
* 把這個指派拿掉。
* 做完這件事之前，不要開始另一個修法。

## 先減再加

* 加任何東西之前，先把複雜度拿掉。

## 以結果為導向的執行

* 瞄準你能檢查的最終狀態。
* 中途可以有中斷，前提是你事先規劃過、而且能還原。

## 打造槓桿

* 如果這個工作不是一眼就看得出怎麼做，就去做一個能做這件事的工具。
* 先手動做一個單位，再讓工具對上那個單位。

## 架構

### 為領域建模

* 把領域放進一個讓非法狀態不可能出現的結構裡。
* 維護一份領域名詞的詞彙表。
* 如果程式碼已經清楚而且是區域性的，就別動它。

### 邊界紀律

* 在資料進來的地方檢查它。
* 進到裡面就信任它。
* 業務邏輯放在純函式裡。

### 型別系統紀律

* 讓非法的值根本寫不出來。
* 外部資料在進來的地方只解析一次。
* 不要讓編譯器閉嘴。

### 讓操作具有冪等性

* 執行兩次，或在中途當機後再執行，最後都會落在同樣的狀態。

### 序列化共享狀態之前先分離

* 如果它們不需要同一個可變的東西，就各給一份。
* 如果需要，就只允許一個寫入者，並且在結構上強制做到。

# 再把它做對（Then Make it Right）

## 修根本原因

* 重現它。
* 修原因。
* 只是把當機遮起來的防護，不算修好。

## 把工作切成可驗證的單位

* 完成一個小單位並檢查它。
* 然後再開始下一個。

## 測試行為，不測實作

* 測試要用使用者呼叫程式碼的方式去呼叫，並檢查使用者會看到的結果。
* 如果每個函式都回傳空值，這個測試還是會通過，那就把它丟掉。

## Crapper

* 使用 crapper 工具
* 把每個函式的 CRAP 分數降到 10 以下，方法是拆分它、測試它，或兩者都做。
* 想想 case 敘述值不值得去降。

## Dryer

* 使用 dryer 工具，消除排名 0.8 以上的重複。

## Mutator

* 使用 mutator 工具
* 補上沒覆蓋到的部分。
* 殺掉存活的 mutant。
* 刪除死碼。

## 重構

* 把程式碼目前的行為釘住。
* 改結構。
* 證明行為沒有變。

# 實務（Practice）

## 記錄日誌

* 把你做的每個動作和原因都記成日誌。
* 完成時回報這份日誌。

## 守護 Context Window

* 讓主執行緒保持精簡。
* 大量的內容送去別的地方，只留摘要。

## Worktree 清理

* 找出可以安全移除的東西，確認沒有還在用的東西需要它，再回收磁碟空間。
* 還沒 commit 的工作要等人決定。

## Commit 與 Push

* 常常 commit，切成小而有順序的 commit。
* 每個 commit 都要說明為什麼改、改了什麼、怎麼證明它沒問題。
* 最後 push 到主線。
