# 設計思考

## 概述

設計思考是一種以人為本的創新方法，整合使用者需求、技術可行性和商業可行性。它的五個階段是迭代的，不是線性的，隨著理解加深，預期會回頭重做。

## 框架

```
IRON LAW: Empathize BEFORE Define, Define BEFORE Ideate
（鐵律：先同理再定義，先定義再發想）

還沒搞懂問題（Define）就跳到解法（Ideate），
會把力氣浪費在解錯的問題上。沒有同理使用者就去定義問題，
只會產出以內部為中心的問題陳述。

順序很重要：先理解人，再框出問題，
然後才產生解法。
```

### 五個階段

**1. 同理（Empathize）**：了解使用者的世界
- 觀察、訪談，沉浸在使用者的情境中
- 目標：理解需求、痛點和動機（不只是他們說了什麼，還有他們做了什麼、感受到什麼）

**2. 定義（Define）**：框出對的問題
- 把同理的發現綜合成一句觀點（POV）陳述：
  `[User] needs to [need] because [insight]`
- 定義得好的問題，等於已經解決一半。需要的話就重新框架。

**3. 發想（Ideate）**：產生很多解法
- 發散：量比質重要。先延後評斷。
- 技巧：腦力激盪、How Might We 問題、SCAMPER、最糟糕的點子
- 然後收斂：投票、分群、選出 2-3 個概念去做原型

**4. 原型（Prototype）**：讓點子變得具體
- 快速、便宜、可丟棄的原型，用來學習
- 擬真度要配合問題：流程用紙本草圖、互動用可點擊的 mock、技術可行性用程式碼
- 目標：測試假設，不是讓利害關係人驚艷

**5. 測試（Test）**：向真實使用者學習
- 把原型放到真實使用者面前
- 觀察行為，不要只問意見
- 什麼有效？什麼失敗？什麼讓你意外？
- 如果核心假設錯了，就回到同理或定義

## 輸出格式

```markdown
# Design Thinking Sprint: {Challenge}

## Empathize
- User: {who}
- Key insights from research: ...
- Surprises: ...

## Define
- POV: [User] needs to [need] because [insight]
- How Might We: {3-5 HMW questions}

## Ideate
- Ideas generated: {count}
- Top 3 concepts: ...

## Prototype
- Prototype type: {paper / digital / physical}
- What it tests: {specific assumption}

## Test
- User feedback: ...
- Validated: {what was confirmed}
- Invalidated: {what was wrong}
- Next iteration: {what to change}
```

## 範例

### 正確的應用
**情境：** 重新設計醫院候診室的體驗
- **同理**：觀察病人 3 天。關鍵洞察：焦慮的高峰不是來自等待時間，而是來自對等待時間的「不確定」。
- **定義**：「病人需要感覺自己知道等候狀態，因為不確定性放大的焦慮，超過實際等待所造成的。」
- **發想**：40 多個點子 → 前 3 名：即時排隊顯示、簡訊位置更新、預估時間自助機
- **原型**：簡訊更新流程的紙本原型（5 分鐘做完）
- **測試**：測了 8 位病人 → 6 位表示感覺「焦慮少很多」，雖然實際等待時間沒變 ✓

### 錯誤的應用
- 跳過同理，一開頭就說「我們需要一個新的 app 功能」 → 沒搞懂問題就先想解法。違反鐵律。

## 常見陷阱

- **「快速失敗」需要心理安全感**：如果失敗會被處罰，團隊就不會去實驗。要讓大家知道，原型本來就是用來失敗的，那就是學習。
- **HMW 問題會決定解法空間**：「我們如何縮短等待時間？」和「我們如何降低等待時的焦慮？」會導向不同的解法。框架要小心。
- **原型 ≠ MVP**：原型是用便宜的方式測試假設。MVP 是可行的產品。不要把原型做過頭。
- **設計思考不只是給設計師用的**：它適用於服務、流程、政策、商業模式，任何涉及人類需求的問題。
- **迭代不是選項**：如果五個階段只跑一遍而沒有回頭，你做的是「貼滿便利貼的瀑布式開發」，不是設計思考。
