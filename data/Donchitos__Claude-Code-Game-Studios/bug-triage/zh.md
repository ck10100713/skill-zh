# Bug Triage

這個 skill 把還開著的 bug backlog 處理成一份排好優先順序、
分派好 sprint 的行動清單。它區分**嚴重度**（影響有多糟？）和
**優先度**（得多緊急修？），偵測系統性趨勢，
並確保沒有任何嚴重 bug 在 sprint 之間被遺漏。

**輸出：** `production/qa/bug-triage-[date].md`

**何時執行：**
- Sprint 開始時：把還開著的 bug 分派到新的 sprint 或 backlog
- `/team-qa` 完成、並且有新 bug 被建檔之後
- bug 數量超過 10 個以上還開著的時候

---

## 1. 解析參數

**模式：**
- `/bug-triage sprint`：針對目前的 sprint 做 triage；把修得了的 bug
  分派到 sprint backlog；其餘延後
- `/bug-triage full`：不管 sprint 範圍，對所有 bug 做完整 triage
- `/bug-triage trend`：只做趨勢分析（不分派）；唯讀報告
- 沒有參數：有目前的 sprint 就跑 sprint 模式，否則跑 full 模式

---

## 2. 載入 Bug Backlog

### Step 2a：找出 bug 檔案

依優先順序 Glob bug 報告：
1. `production/qa/bugs/*.md`：個別的 bug 報告檔（偏好的格式）
2. `production/qa/bugs.md`：單一整合的 bug 紀錄（備用）
3. 任何 `production/qa/qa-plan-*.md` 的 "Bugs Found" 表（最後手段）

如果找不到 bug 檔案：
> "No bug files found in `production/qa/bugs/`. If bugs are tracked in a
> different location, adjust the glob pattern. If no bugs exist yet, there is
> nothing to triage."

停下來並回報。沒有 bug 就不要繼續。Verdict: **COMPLETE** — no bug files in `production/qa/bugs/`; nothing to triage.

**在 `trend` 模式，不要讀完整的 bug 內文。** 趨勢指標（數量、嚴重度
分布、依系統、依日期）光靠標頭欄位就算得出來：
```
Grep pattern="\*\*(Severity|Priority|Status|System|Category|Reported)\*\*" glob="production/qa/bugs/*.md" output_mode="content"
```
（Bug-report 的欄位是粗體，`**Severity**:`、`- **System**:`，所以要比對
`**field**` 這個形式，不是行首的 `Field:`。）
只有 `sprint`/`full` 模式的優先度 vs 嚴重度**重新評估**才需要完整的 bug 內文；
`trend` 是唯讀報告，會跳過它。（唯一需要 story 狀態的
偏差檢查，「bug 開在已完成的 story 上」，不管哪種都是針對性的 story 狀態 grep，不是讀 bug 內文。）

### Step 2b：載入 sprint context

讀 `production/sprints/` 裡最近修改的檔案，了解：
- 目前的 sprint 編號／名稱
- 範圍內的 stories（作為分派的目標）
- Sprint 容量限制（如果有註明）

如果沒有 sprint 檔案：註明 "No sprint plan found — assigning to backlog only."。在 `workflow: minimal`，依設計本來就沒有 sprint，要改說這件事，並把 P1 bug 指為下一批修正，排在 brief 的 build order 裡下一個 story 之前。

### Step 2c：載入嚴重度參考

如果 `.claude/docs/coding-standards.md` 有嚴重度／優先度定義，就讀它。如果沒有，
就用 Step 3 的標準定義。

---

## 3. 分類每個 Bug

每個 bug 都要擷取或推斷：

### Severity（bug 的影響）

| Severity | Definition |
|----------|-----------|
| **S1 — Critical** | Game crashes, data loss, or complete feature failure. Cannot proceed past this point. |
| **S2 — High** | Major feature broken but game is still playable. Significant wrong behaviour. |
| **S3 — Medium** | Feature degraded but a workaround exists. Minor wrong behaviour. |
| **S4 — Low** | Visual glitch, cosmetic issue, typo. No gameplay impact. |

### Priority（修正的緊急程度）

| Priority | Definition |
|----------|-----------|
| **P1 — Fix this sprint** | Blocks QA, blocks release, or is regression from last sprint |
| **P2 — Fix soon** | Should be resolved before the next major milestone |
| **P3 — Backlog** | Would be good to fix, but no active blocking impact |
| **P4 — Won't fix / Deferred** | Accepted risk or out of scope for current product scope |

### 分派

`sprint` 模式下，每個 P1/P2 bug：
- 找出這個修正屬於哪個 story 或 epic
- 檢查目前的 sprint 還有沒有剩餘容量
- 有容量：分派到 sprint（`Sprint: [current]`）
- 容量滿了：標記為 `Priority overflow — consider pulling from sprint`

`full` 模式：所有 P1 分派到目前的 sprint，P2 分到預估的下一個 sprint，
P3 以下放 backlog。

### 偏差檢查

標記暗示**系統性問題**的 bug：
- 同一個 sprint 裡同一個系統有 3 個以上 bug → "Potential design or
  implementation quality issue in [system]"
- 同一個 story 有 2 個以上 S1/S2 bug → "Story may need to be reopened and
  re-reviewed before shipping"
- bug 開在已標記 Complete 的 story 上 → "Regression in completed story —
  story should be re-opened in sprint tracking"

---

## 4. 趨勢分析

分類完所有 bug 之後，產生趨勢指標：

### 數量趨勢
- 還開著的 bug 總數：[N]
- 這個 sprint 新開的：[N]
- 這個 sprint 關閉的：[N]
- 淨變化：[+N / -N]

### 系統熱點
- 哪個系統還開著的 bug 最多？
- 哪個系統的 S1/S2 比例最高？

### 存活時間分析
- 有多少 bug 超過 2 個 sprint 了？
- 有沒有任何 S1/S2 bug 沒分派（sprint = none）？

### Regression 指標
- 有沒有任何 bug 開在先前已完成的 story 上？
- 數量：[N] 個 regression bug（意味著 story 要重開）

## 6. 寫入與把關

在對話裡呈現報告。如果有任何 bug 是 P4 候選，先問
"Are these acceptable as Won't Fix?"，在使用者回答之前，
它的處置維持 `P4 candidate`。然後問：

"May I write this triage report to `production/qa/bug-triage-[date].md`?"

核准後才寫。

寫完之後：
- 如果有任何 S1 bug 沒分派："S1 bugs must be assigned before the sprint
  can be considered healthy. Run `/sprint-status` to see current capacity."
- 如果有 regression bug："Regressions found — consider re-opening the
  affected stories in sprint tracking and running `/smoke-check` to re-gate."
- 如果沒有 P1 bug："No P1 bugs — build is in good shape for QA hand-off."

然後，不管有沒有 P1 bug：Verdict: **COMPLETE** — triage report written.

如果使用者拒絕寫入：Verdict: **BLOCKED** — user declined write.

---

## 協作協定

- **沒有使用者核准，絕對不要關閉 bug 或把它標成 Won't Fix**，
  把它們當成 P4 候選呈現，然後問："Are these acceptable as Won't Fix?"
- **絕對不要自動分派到已滿載的 sprint**：標記溢出，讓
  sprint 負責人決定要拉哪些進來
- **嚴重度是客觀的；優先度是團隊的決定**：嚴重度分類
  當成建議呈現，不是命令
- **趨勢資料只供參考**：不要光憑趨勢發現就擋住工作；
  把它們當成觀察呈現
