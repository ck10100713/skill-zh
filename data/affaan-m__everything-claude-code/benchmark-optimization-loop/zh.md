# Benchmark Optimization Loop

用這個 skill 把「讓它快 20 倍」或「嘗試 50 輪遞迴最佳化」
轉成有界限、可量測、而且真的能改善系統的迴圈。

## 必要的基準線

這些東西沒齊之前，不要開始最佳化：

- 要最佳化的操作；
- 必須維持通過的正確性關卡；
- 指標：實際耗時、p95 延遲、每秒列數、每次執行的成本、記憶體、錯誤率；
- 目前的基準線；
- 搜尋預算：最多幾個變體、最長時間、最高花費、最大的資料影響。

如果使用者要求不切實際的目標，保留那份企圖心，但要讓迴圈
有界限、可量測。

## 迴圈

1. 量測基準線。
2. 依證據找出瓶頸。
3. 產生變體，每個變體只驗證一個假設。
4. 用相同形狀的輸入執行這些變體。
5. 淘汰在正確性、安全性或可重現性上失敗的變體。
6. 升級最快且安全的變體。
7. 把勝出的路徑寫成 script、指令、測試、設定或文件固定下來。
8. 重跑基準線和勝出者，確認差異。

## 變體表

像這樣追蹤變體：

```text
Variant | Hypothesis | Command | Time | Correct? | Notes
baseline | current path | npm run job | 120s | yes | stable
batch-500 | fewer round trips | npm run job -- --batch 500 | 42s | yes | winner
parallel-8 | more workers | npm run job -- --workers 8 | 31s | no | rate limited
```

## 遞迴搜尋

遞迴或超參數的工作：

- 把每次執行都持久化到帳本裡；
- 跟前一個被接受的勝出者比較，不要只跟上一次執行比；
- 保留一個 holdout 或重放檢查；
- 當改善幅度落在雜訊範圍內、正確性失敗、成本超出
  預算，或搜尋開始改動超過它能解釋的變數數量時，就停下來。

除非搜尋空間真的窮舉過了，否則要用「實測最佳的安全變體」這種說法，不要說「全域最佳解」。

## 升級關卡

變體要通過以下條件，才能成為新的預設值：

- 正確性測試通過；
- 效能差異已重複驗證或已有解釋；
- 回復的方式很明確；
- 這個修改已經寫進版本控制或持久的 runbook；
- 最後的摘要包含確切的指令和量測數據。
