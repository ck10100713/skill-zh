# Agent 自我評估

完成複雜任務之後，agent 停下來，用結構化的五面向評分標準替自己的產出打分。這不是通過或不通過的關卡，而是刻意的反思步驟，能在使用者發現之前，先抓出遺漏、標出過度自信，並找出可以改進的地方。

## 何時啟用

- 寫了橫跨 3 個以上檔案或 50 行以上的程式碼之後
- 完成多步驟工作流程（實作 → 測試 → review）之後
- 經過 3 次以上嘗試的除錯過程之後
- 產出設計文件、架構決策或書面分析之後
- 使用者問「剛剛做得怎麼樣？」或「幫自己打個分」的時候
- 任何 session 結束的 Stop hook（如果有設定，見 `references/hook-integration.md`）

## 核心概念

### 五個評估面向

| 面向 | 問題 | 抓得到什麼 |
|---|---|---|
| **正確性（Accuracy）** | 事實、主張和輸出是正確的嗎？ | 幻覺、錯誤的 API 名稱、不正確的語法、錯誤的陳述 |
| **完整性（Completeness）** | 使用者要求的每一項都涵蓋了嗎？ | 漏掉的 edge case、沒處理的錯誤路徑、被遺忘的需求、跳過的子任務 |
| **清晰度（Clarity）** | 說明容易理解、結構良好嗎？ | 令人困惑的說明、沒定義的術語、缺少 context、囉嗦離題 |
| **可執行性（Actionability）** | 使用者能馬上依據這份輸出行動嗎？ | 模糊的建議、缺少的步驟、只說「你應該 X」卻沒示範怎麼做、沒有驗證路徑 |
| **精簡度（Conciseness）** | 有用最少的字數或 token 嗎？ | 重複、過度解釋、逐字複述使用者的問題、填充內容 |

### 評分量表

```
5 — 卓越：沒有合理的改進空間
4 — 良好：只有小瑕疵，沒有實質缺口
3 — 堪用：符合要求，但至少一個面向有明顯的弱點
2 — 偏弱：有明確的缺口，影響可用性或正確性
1 — 不佳：根本沒達成要求，或含有重大錯誤
```

### 證據規則

每個低於 5 的分數，一定要引用具體證據。給 3 分不能只寫「可以更好」，必須明確說出缺了什麼或錯在哪。口訣是：**「把缺口秀出來，不要只是點名。」**

## 工作流程

### 步驟 1：蒐集原始素材

收集你要評估的東西：

```
- 使用者原本的需求（從對話中讀回來）
- 你最終的回應或輸出（交付物）
- 任何能驗證正確性的工具輸出（測試結果、exit code、lint 輸出）
- 任務過程中收到的任何使用者回饋（更正、「再試一次」、「這不對」）
```

### 步驟 2：獨立替每個面向打分

一次處理一個面向。每個面向都這樣做：

1. 讀這個面向的問題
2. 在輸出中找證據（或缺乏證據的地方）
3. 給 1 到 5 的分數
4. 如果分數低於 5，寫一句引用缺口的改進筆記

不要先在腦中算平均，再倒推各面向的分數。每個面向都要重新獨立打分。

### 步驟 3：產出評估報告

使用 `templates/evaluation-report.md` 的範本。報告必須包含：

```
- 一句話摘要
- 五面向評分表（每個面向的分數加證據）
- 總分（簡單平均，四捨五入到小數點後一位）
- 1 到 3 項依影響大小排序的具體改進
- 自我檢查：「使用者會同意這個評估嗎？」
```

### 步驟 4：套用改進

如果任何面向得到 3 分或以下：

1. 說明你會怎麼做得不一樣
2. 如果缺口 30 秒內就能修好（缺少的連結、不清楚的措辭），現在就修
3. 如果缺口需要重做，明確標出來：「這個面向得到 [原因] 的分數，因為 [證據]。用 [具體修正] 重跑，很可能升到 [分數]。」

## 程式碼範例

### 範例：好的評估（4 分以上）

```
任務：幫 HTTP client 加上重試邏輯

評分表：
  正確性：    5 — 所有 API 呼叫都正確。已驗證：重試使用
                  exponential backoff。沒有幻覺出來的方法。
  完整性：    4 — 涵蓋 happy path 加 3 種錯誤情況。缺少：
                  卡住連線的 timeout 處理。
  清晰度：    5 — 程式碼註解說明了 backoff 公式。
                  PR 描述連結到促成這次修改的事故。
  可執行性：  5 — 一次 merge 完成。沒有後續任務。測試通過。
  精簡度：    4 — 總共 47 行。重試迴圈可以抽成 helper，
                  大約少 8 行。

總分：4.6 — 一個缺口（timeout 處理）。merge 之前先修好。
```

### 範例：偏弱的評估（2 到 3 分）

```
任務：幫 HTTP client 加上重試邏輯

評分表：
  正確性：    2 — 用了 urllib3，跟我們以 httpx 為基礎的
                  codebase 不合。用錯函式庫。
  完整性：    3 — GET 可以用。POST/PUT 沒處理（使用者
                  說的是「所有 HTTP 請求」）。
  清晰度：    4 — 程式碼好讀。變數名稱不錯。
  可執行性：  2 — 提到「加測試」，但沒建立測試檔。
                  使用者 merge 前得自己寫測試。
  精簡度：    3 — 120 行。重試設定在 3 個地方重複，
                  沒有共用一個 RetryConfig 物件。

總分：2.8 — 用錯函式庫。需要用 httpx 重寫。
  先修正確性（換成 httpx），再擴充到所有
  HTTP method，最後整合設定。
```

## 反面模式

### 「每項都是 5 分」

```
FAIL: 正確性：    5 — 都很好。
   完整性：    5 — 全部涵蓋。
   清晰度：    5 — 很清楚。
```

沒有引用證據。這是自我感覺良好，不是評估。真正的 5 分，必須證明已經沒有東西可以改進。

### 因為範圍擴張而過度扣分

```
FAIL: 完整性：2 — 沒處理 WebSocket 連線或
   gRPC streaming（使用者沒要求這些）
```

只對照使用者真正要求的東西來評估，不要拿你「本來還可以多做的」來扣分。

### 拿評估來重新翻案

```
FAIL: 「我之前就說過，這個做法是錯的。分數：1」
```

評估針對的是交付出去的產出，不是重新爭論已經做過的設計決定。如果做法有問題，應該在交付前就抓到。

### 把個人偏好跟客觀缺口混在一起

```
FAIL: 「分數：3。我不喜歡 Python decorator。」
```

「不喜歡」不是證據。要引用具體的可讀性、可測試性或正確性問題，不然分數就留在 4 分以上。

## 最佳實務

- **評估輸出，不是過程。** 使用者在意的是你交付了什麼，不是你試了幾輪。
- **每個弱的面向只提一項改進。** 不要在一個面向底下列 5 件事，挑影響最大的缺口。
- **把改進跟對使用者的影響連起來。** 「少了錯誤處理，使用者的 API 呼叫會無聲無息地崩掉」比「加上錯誤處理」好。
- **具體說明「修好」長什麼樣子。** 「用設定好重試的 httpx transport 重跑」比「修正函式庫的問題」好。
- **用工具輸出當證據。** 測試通過就引用測試，lint 乾淨就引用 lint。不要用猜的，用 grep 找證明。
- **如果你找不到任何缺口，再努力找一下。** 五個面向全拿滿分很少見。問自己：「如果我是使用者，這份輸出哪裡會讓我不爽？」
